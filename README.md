# DRISHTI · दृष्टि
**D**isaster **R**isk **I**ntelligence & **S**ituational **H**azard **T**racking **I**nterface

A MongoDB-based big-data analytics platform for flood and emergency intelligence.
Project: *Disaster & Emergency Intelligence System* — Big Data Analytics (BIS701), Dept. of ISE, Bangalore Institute of Technology, 2026-27.

## What it does
| Synopsis requirement | Where it lives |
|---|---|
| Store large disaster datasets in MongoDB | `server/src/seed.js` — 3.6 M time-series documents, 46 risk zones, 900 historical events |
| Analyse historical + real-time data | `server/src/live.js` simulated live feed, `server/src/analytics.js` pipelines |
| High-risk areas on a map (location data) | 2dsphere indexes, `$geoNear`, `$geoWithin`; Map page |
| Detect unusual rainfall / river / weather changes | baseline (`$stdDevPop`, `$percentile` → `$merge`) + z-score & rate-of-rise anomaly pipeline |
| Interactive dashboard | React + Recharts + React-Leaflet (`client/`) |
| Reports & insights | Reports page → stored in the `reports` collection |
| Disaster patterns for authorities | Analysis page (`$facet` history, seasonality, regional ranking) |

## Design
The UI follows a written design system, [DESIGN.md](DESIGN.md): a flood-bulletin aesthetic (ink on paper, ruled tables, numbered sections, severity encoded by glyph shape as well as colour). Tokens live in `client/src/tokens.js`; fonts are self-hosted so the app works offline.

## Stack
React 19 + Vite · Recharts · React-Leaflet (+ leaflet.heat) · Node.js + Express · MongoDB 7 (time-series collections, aggregation pipelines, 2dsphere).

## Run
```powershell
.\start.ps1            # MongoDB in Docker (port 27019), builds UI, serves everything on http://localhost:5055
.\start.ps1 -Reseed    # regenerate the dataset first (~35 s)
```
Manual: `docker compose up -d` → `cd server && npm i && npm run seed && npm start` → `cd client && npm i && npm run build`.

Dev mode: `cd client && npm run dev` (Vite proxies `/api` to :5055).

## Data model (MongoDB `drishti`)
| Collection | Purpose |
|---|---|
| `stations` | 138 gauges, GeoJSON `location` (2dsphere), flood thresholds, `zoneId` |
| `rainfall_records`, `river_levels`, `weather_data` | **time-series** collections (`ts`, meta `stationId`), hourly |
| `risk_zones` | GeoJSON polygons (2dsphere) with classification |
| `disaster_events` | historical events, 2dsphere + date index |
| `station_baselines` | per-station mean/σ/p95/p99 built by an aggregation `$merge` |
| `risk_snapshots` | risk score per station per tick (risk history) |
| `alerts` | alert lifecycle: active → escalated → resolved |
| `reports` | generated situation reports |
| `sim_state` | simulator clock and per-station state for the live feed |

## Risk model
`score = 100 × (0.5·levelPct + 0.3·rainZ + 0.2·riseRate)` — each term normalised to 0–1:
`levelPct` = (level − base)/(danger − base) · `rainZ` = (6 h mean rain − μ)/σ ÷ 6 · `riseRate` = m/h ÷ 0.4.
Severity: ≥70 CRITICAL, ≥50 HIGH, ≥30 ELEVATED. Anomaly = rain z ≥ 3σ, level z ≥ 3σ, or rise ≥ 0.25 m/h.

## Honest data note
All sensor readings and historical events are **synthetic** (generated by a hydrological-style simulator in `server/src/sim.js`) as permitted by the synopsis. Gauge names/locations use real flood-prone cities, but values are not real measurements. The "live" feed advances the simulated clock one hour per ~6 s, and pauses when nobody is viewing.
